## 1. 회원 관리 웹 애플리케이션 요구사항
- **회원 정보**: `id`(식별자 번호), `username`(이름), `age`(나이)
- **기능 요구사항**: 회원 저장, 회원 목록 조회
- **회원 저장소(`MemberRepository`)**
  - 자바 싱글톤 패턴 적용 (생성자를 `private`으로 차단, `getInstance()` 제공)
  - 메모리 맵 기반 저장소 구현 (실무 동시성 처리 고려 시 `ConcurrentHashMap`, `AtomicLong` 사용 권장)

## 2. 서블릿 기반 구현과 한계점

### 1) 서블릿으로 화면과 로직 동시 처리
- `MemberFormServlet`: HTML Form 코드를 자바 서블릿의 `PrintWriter` 스트림으로 직접 출력
- `MemberSaveServlet`: 요청 파라미터를 받아 객체 생성 및 저장 후, 결과 HTML을 동적으로 생성
- `MemberListServlet`: 저장된 회원 목록을 조회하여 HTML 반복문(`for`)으로 동적 렌더링

### 2) 서블릿의 치명적인 한계
- 동적 화면 생성을 위해 순수 자바 코드 안에서 수많은 HTML 문자열을 일일이 출력해야 함
- 코드 가독성이 극도로 떨어지고 복잡하며, 오타 발생 및 유지보수가 비효율적임
- **결론**: 자바 코드 기반에 HTML을 넣는 것이 아니라, HTML 문서 안에 동적 코드만 삽입하는 **템플릿 엔진**의 필요성 대두

---

## 3. JSP 기반 구현과 한계점

### 1) JSP를 활용한 뷰 생성
- HTML 중심 구조에 자바 코드를 스크립틀릿 태그(`<% %>`, `<%= %>`) 형태로 삽입
- 서블릿보다 HTML을 작성하고 시각적으로 다루는 것이 훨씬 수월해짐
- JSP 파일은 서버 내부에서 결국 서블릿 클래스로 자동 변환되어 동작함

### 2) JSP의 한계
- **너무 많은 책임 부담**: 비즈니스 로직(저장, 조회 등), 리포지토리 접근, 화면 렌더링 코드가 하나의 JSP 파일에 혼재됨
- **유지보수 지옥**: 화면 디자인 변경 하나를 위해 수백 줄의 자바 비즈니스 코드를 파헤쳐야 함
- **라이프사이클의 불일치**: UI 변경 주기와 비즈니스 로직 변경 주기가 완전히 다른데 단일 파일에 묶여 있어 유지보수에 악영향을 미침

## 4. MVC 패턴의 등장 및 개요

하나의 서블릿/JSP가 모든 것을 처리하던 방식에서 벗어나 **역할을 명확히 분리**

- **컨트롤러 (Controller)**
  - HTTP 요청을 수신하고 파라미터를 검증
  - 실제 비즈니스 로직(서비스 계층)을 호출 
  - 뷰에 전달할 데이터를 생성하여 모델에 보관 
- **모델 (Model)**
  - 뷰가 렌더링할 때 필요한 데이터만 담아두는 보관함 
  - 뷰는 비즈니스 로직이나 DB 접근 방식을 몰라도 모델의 데이터만으로 화면 구성 가능 
- **뷰 (View)**
  - 모델에 담겨있는 데이터만을 참조하여 최종 HTML 화면을 렌더링하는 역할에만 집중 

---

## 5. 서블릿 & JSP MVC 패턴 실전 적용

### 1) 역할 분담
- **컨트롤러**: 서블릿 (`HttpServlet`) 
- **뷰**: JSP (`/WEB-INF/views/*.jsp`) 
- **모델**: `HttpServletRequest` 내부의 임시 데이터 저장소 
  - 데이터 저장: `request.setAttribute(key, value)` 
  - 데이터 조회: `request.getAttribute(key)` 또는 JSP의 EL 표기법(`\${key.property}`) 

### 2) 주요 메커니즘
- **`RequestDispatcher.forward()`**: 서블릿에서 처리를 마친 후 JSP 화면으로 제어권을 넘김 (클라이언트 모르게 서버 내부에서 위임 호출) 
- **`/WEB-INF` 디렉터리 보호**: 브라우저에서 URL로 직접 JSP에 접근하는 것을 원천 차단하고, 반드시 서블릿(컨트롤러)을 통해서만 포워드되도록 강제 
- **JSTL (`<c:forEach>`)**: 지저분한 자바 `for`문 대신 태그 라이브러리를 통해 리스트 데이터를 깔끔하게 반복 출력 

---

## 6. 순수 서블릿 MVC 패턴의 한계

MVC를 적용하여 화면과 로직은 분리되었으나, 여전히 컨트롤러 단에서 구조적 비효율이 발생 :

- **포워드 코드의 지속적인 중복**: 모든 컨트롤러마다 `RequestDispatcher` 생성 및 `forward()` 호출 반복 
- **ViewPath 경로 중복**: prefix(`/WEB-INF/views/`)와 suffix(`.jsp`)가 매번 중복 하드코딩되어 뷰 템플릿 교체 시 전체 컨트롤러 수정 필요 
- **사용하지 않는 매개변수 의존**: 화면 이동만 하는 컨트롤러에서도 불필요하게 `HttpServletResponse` 등을 파라미터로 받아야 하며, 이는 단위 테스트 작성을 어렵게 만듦 
- **공통 기능 처리의 한계**: 인가, 로깅, 공통 파라미터 처리 등 컨트롤러 전반에 걸친 공통 로직을 메서드로 빼더라도 매번 직접 호출해야 하는 누락 위험과 코드 중복이 남음 

> **해결책의 방향성**  
> 컨트롤러 호출 직전, 맨 앞에서 모든 요청을 일괄 접수하고 공통 작업을 처리해 주는 수문장 역할의 **프론트 컨트롤러(Front Controller) 패턴**의 도입 필요 (스프링 MVC의 `DispatcherServlet`의 핵심 구조) .
