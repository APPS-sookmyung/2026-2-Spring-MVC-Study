## 1. 웹 서버 vs WAS (Web Application Server)

### 개념 비교
- **웹 서버 (Web Server)**
  - HTTP 기반 정적 리소스(HTML, CSS, JS, 이미지 등) 제공
  - 예시: `NGINX`, `Apache`
- **웹 애플리케이션 서버 (WAS)**
  - HTTP 기반 정적 리소스 + 프로그램 코드 실행(비즈니스 로직 수행)
  - 동적 HTML 생성 및 HTTP API 제공
  - 예시: `Tomcat`, `Jetty`, `Undertow`

### 권장 아키텍처: `Client -> Web Server -> WAS -> DB`
- **분리 이유**
  - **효율적 리소스 분배**: 정적 요청 폭증 시 Web 서버 증설, 로직 부하 증가 시 WAS 증설
  - **안정성 확보**: 정적 리소스만 처리하는 Web 서버는 잘 다운되지 않음
  - **장애 대응**: WAS나 DB가 다운되어도 Web 서버가 오류 안내 페이지 노출 가능

## 2. 서블릿 (Servlet)

### 서블릿의 역할
- 개발자가 HTTP 프로토콜 파싱/패킷 조립을 직접 하지 않고 **비즈니스 로직에만 집중**할 수 있도록 지원
- WAS가 HTTP 요청/응답을 파싱하여 `HttpServletRequest`, `HttpServletResponse` 객체로 제공

### 서블릿 컨테이너 특징
- **생명주기 관리**: 서블릿 객체의 생성, 초기화, 실행, 소멸을 WAS가 자동 관리
- **싱글톤 패턴**: 
  - 요청마다 객체를 생성하지 않고, 최초 로딩 시 1개만 생성하여 재사용
  - **주의**: 모든 쓰레드가 공유하므로 **공유 변수(상태값) 사용 시 Thread-safe 문제 주의**
- **멀티 쓰레드 지원**: 동시 요청 처리를 위한 쓰레드 풀 연동

## 3. 멀티 쓰레드와 쓰레드 풀 (Thread Pool)

### 요청마다 쓰레드 생성 시 문제점
- 쓰레드 생성/종료 비용으로 인한 응답 지연
- CPU 컨텍스트 스위칭 오버헤드 급증
- 동시 요청 폭증 시 서버 다운(OOM, 리소스 고갈)

### WAS의 쓰레드 풀 방식
- 미리 정해진 수량(Tomcat 기본: 200개)만큼 쓰레드를 만들어 풀에 보관
- **동작**: `요청 -> 풀에서 쓰레드 대여 -> 로직 수행 -> 풀에 반납`
- 풀에 쓰레드가 없으면 대기(Queue) 또는 요청 거절

### 실무 성능 튜닝 핵심
- **최대 쓰레드 수(Max Thread)** 조절이 핵심 포인트
  - 너무 낮음: 서버 리소스는 널널한데 동시 처리량 저하
  - 너무 높음: 동시 부하 시 CPU/메모리 한계 초과로 서버 셧다운
- 애플리케이션 로직 복잡도, I/O 대기 시간에 맞춰 부하 테스트(`nGrinder`, `JMeter`, `ab`) 후 결정
- 개발자는 멀티 쓰레드 관리 코드를 직접 짜지 않아도 되지만, **싱글톤 빈 내부의 동시성 이슈**는 반드시 인지해야 함

## 4. 웹 렌더링 & 통신 방식

### HTTP API vs 정적 리소스
- **정적 리소스**: 변경 없는 HTML, CSS, JS, 파일 반환
- **HTTP API**: 주로 `JSON` 포맷으로 순수 데이터만 송수신 (모바일 앱, SPA 프론트엔드, 서버 간 통신)

### SSR vs CSR
- **SSR (Server-Side Rendering)**
  - 서버에서 HTML 화면을 완성해서 브라우저로 전송
  - 기술: `JSP`, `Thymeleaf`
  - 특징: 검색 엔진 최적화(SEO) 유리, 초기 로딩 빠름
- **CSR (Client-Side Rendering)**
  - 서버는 JSON 데이터만 주고, 브라우저에서 JS가 동적으로 DOM 렌더링
  - 기술: `React`, `Vue.js`
  - 특징: 화면 깜빡임 없는 인터랙티브 앱 구현에 유리

## 5. 자바 백엔드 기술의 변천사

- **서블릿 (1997)**: 순수 자바 코드 안에서 HTML을 출력(스트림)해야 해서 유지보수 극악
- **JSP (1999)**: HTML 작성은 편해졌으나 비즈니스 로직과 뷰 코드가 한곳에 섞여 비대해짐
- **MVC 패턴 & 프레임워크 춘추전국시대**: Model, View, Controller 분리 (`Struts`, `WebWork`, 초기 `Spring MVC`)
- **애노테이션 기반 Spring MVC**: `@Controller`, `@RequestMapping` 등을 통해 유연하고 직관적인 개발 완성
- **Spring Boot의 혁신**: 
  - 과거: WAS를 서버에 별도 설치 후 War 파일 빌드/배포
  - 현재: **내장 톰캣** 탑재로 실행 가능한 단일 Jar 파일 배포 (배포 프로세스 단순화)
- **Spring MVC vs WebFlux**:
  - `Spring MVC`: 쓰레드 풀 기반 동기/블로킹 방식 (실무 대부분의 표준)
  - `Spring WebFlux`: Netty 기반 비동기/논블로킹, 최소 쓰레드로 대규모 동시 요청 처리 (학습 난이도 높음, RDB 연동 제약 등으로 특수 목적에 주로 사용)
